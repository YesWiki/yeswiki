# The component palette offers Components, not Actions

The editor's palette has always looked like a view of the action list, and it has never been one. Today there are **105 registered actions and 70 palette entries**, disagreeing in both directions: 51 actions have no entry at all (`col`, `tab`, `map`, `calendar`, `entrytable`, `toc`, `favicon`, `metarobots`, `pagetitle`, `breadcrumb`…) and 16 entries are not actions. Twelve of those sixteen are `docs/actions/entrylist.yaml`'s presentations — `bazarcard`, `bazarblog`, `bazarannuaire`, `bazartimeline` — which all write `{{entrylist template="…"}}` through a hardcoded special case in `javascripts/actions-builder-app.js`:

```js
let actionId = this.selectedActionId
if (this.isEntryListAction) actionId = 'entrylist'
```

So the thing a webmaster picks was already not an action; it was only admitted for one group, in JavaScript.

We decided to name the palette's unit and give it a declaration of its own. A **Component** is something insertable into page content: it knows its label, its icon, its settings, and how to write itself — and what it writes is always a `{{tag}}`. One Component may write more than one action, and several may write the same action with different settings. Three further terms fall out of it, all in `CONTEXT.md`: a **Presentation** is a Component that renders a list of **Items** in one shape (Cards, Table, Accordion, Map, Calendar, Timeline), and a **Source** is an action that supplies Items rather than rendering anything — `entrylist` over a form, `syndication` over a feed, `listpages` over pages. A Source has **no palette entry**: it appears inside the source setting of every Presentation. So `Cards` is one Component that writes `{{entrylist id="x" template="card"}}` or `{{syndication url="…" template="card"}}` depending on where its items come from, and looks the same either way.

The boundary that keeps this simple is that **markup syntax is the toolbar's, `{{tags}}` are the palette's**. The `:::info` callouts started as the motivating case for putting non-action things in the palette; they end up in the editor toolbars instead, next to `{# comment #}` and `highlight`, which are already there and are already the same kind of thing — notation you reach by formatting text rather than by inserting a component. The ACeditor toolbar's `surroundSelectionWith(lft, rgt)` over its `DELIMITERS` map is exactly the mechanism a callout needs, and a toolbar item applied to text that already carries it retypes it, the way a heading level does. So a Component is recognised by its tag, with no second rule for the one thing that had no tag — and every future markdown construct (footnotes, definition lists) has a home that is not the Component model.

Components are declared in **PHP**, not in `docs/actions/*.yaml`. An interface returning a list of typed value objects; an action may implement it for its own components, and anything with no action (the callouts) declares through a standalone provider of the same interface. Discovery is by DI tag, exactly like `RegisteredAction` — no registry to enrol in. The YAML path is deleted everywhere: core's 2409 lines, `extensions/*/actions/documentation.yaml` and `custom/actions/documentation.yaml`. `docs/actions/` goes with it, catalog included — its 553 keys merge into `src/lang/`, and `YesWikiRuntime`'s `$this->extensions['actionsbuilder']` line (a directory registered as a fake extension purely so its `lang/` would load) goes away.

## Considered options

- **Give the callouts a real `{{alert}}` action**, so "one palette entry per action" could stay literally true — rejected. It would leave `:::info` and `{{alert}}` as two syntaxes for one thing, and the editor would have to decide which to write. The problem is not that callouts lack an action; it is that the palette's unit was never an action.
- **Let a Component match markdown as well as a tag**, so the callouts could be palette entries — this was the design for most of the session, and was dropped. It bought the callouts a settings rail at the price of a recognition rule with two clauses, one of which existed for a single case. Putting them in the toolbar costs the rail and buys a rule with no exceptions; the rail was not worth much anyway, since a callout's only setting is the thing the toolbar item already is.
- **A second palette for markdown-level blocks**, leaving the actions builder untouched — rejected. Markup syntax already has a home in both editors — the ACeditor's Format dropdown, Vditor's toolbar — and a third surface would be one more place to look.
- **Keep a data file, move it to PHP arrays** — rejected. The reason to leave YAML is that nothing checks it: sixteen entries point at actions that no longer exist and fifty-one actions have no entry, and neither fact surfaces anywhere. A plain array is YAML with different punctuation.
- **Declare components only in separate provider classes, never on the action** — not chosen. Cleaner on paper, but the parameters an action reads and the settings the palette offers are the same list, and keeping them in two files is how they drifted apart in the first place. A provider stays available for anything with no action to hang off.
- **Unify the list actions into one `{{list source=… template=…}}`** — rejected for now. The data model finally allows it (since ADR-0011 everything is Content, and `formAndListIds()` already returns Page/User/File forms alongside ordinary ones), and it is the most coherent end state. But it rewrites wiki syntax in every existing wiki and needs a body-rewriting migration; ticket 33's went wrong in a way a green test suite could not see. The Source/Presentation split gets most of the coherence with none of the migration, and leaves this reachable later.
- **Make a feed a Data source that imports, so there is literally one renderer** — rejected as the general answer. It is the right shape for configured, repeated syncs (ticket 28/34) and that stays. But a webmaster pasting a feed URL into a page cannot configure a `dataSources` entry, so live feed embedding has to keep working.
- **`position` integers per Component** instead of core-declared categories — rejected. It is the mechanism that produced `2, 3, 4, 1000×7, 1997, 1998, 1999, 2000` across sixteen files, and an extension author has no way to know what number to pick. "Most useful for page editing" is an editorial judgement and belongs in one ordered list.

## Consequences

Every third-party extension shipping an `actions/documentation.yaml` must port it to PHP; `custom/actions/documentation.yaml` loses its no-code escape hatch. Accepted as a MAJOR-release break — a second declaration path is what let the two lists drift.

`{{panel}}` loses its four semantic colour variants, which duplicate what a callout means, and gains a free colour/class instead: **a callout carries meaning, a Panel carries styling**. The Bootstrap-derived `panel-info`/`panel-warning`/`panel-success`/`panel-danger` classes stay styled for stored content under ADR-0004's legacy-vocabulary rule; they simply stop being offered. Note this splits the two across surfaces — the callout is in the toolbar and the Panel is in the palette — which is right, but it means neither one can advertise the other, so the help text on each has to.

Callouts gain no settings rail, so an extension cannot add a `:::` type the way it can add a Component. `AlertExtension::TYPES` is a core constant and always was, so nothing is lost today; it is a door this closes rather than one it opens.

`entrylist` and `syndication` stop having palette entries of their own. A webmaster looking for "entry list" finds Cards, Table and Accordion, and picks the form afterwards. Anything that lists things and is not one of the declared Presentations becomes invisible until it declares itself a Source.

Adding a new Source is a change to that action alone — never to the Presentations. That inversion is the point of the split, and it is what a reviewer should check any future list-rendering action against.
